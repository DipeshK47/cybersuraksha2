अदिति डिसीजन lab में तय token वाला नकली रिसोर्स डेस्क खोलती है। विहान पट्टी को allocated और remaining counter में बाँटता है। हर माने या अस्वीकार request के बाद दोनों का जोड़ शुरुआती कुल के बराबर रहना चाहिए।

मान्य request token remaining से allocated ले जाता है। request पहचान सिर्फ़ सफल स्वीकृति पर याद रहती है। अदिति दोनों counter लिखती है: एक घटाकर दूसरा न बढ़ाना इकाइयाँ खोता है।

विहान remaining से ज़्यादा tokens माँगता है। सुधरा process पहले capacity check करता है और request मना होने पर दोनों counters वही रखता है। Remaining को negative कर देने से कुल जोड़ बच सकता है। फिर भी यह अलग condition तोड़ेगा कि बची quantity negative नहीं होनी चाहिए। ऐसा allocation allowed नहीं है।

पहले माना request उसी पहचान से फिर आता है। तय करें क्या बची क्षमता अकेले उसे दो बार करने का कारण है। अदिति counter के साथ पहचान जाँचती है, ऐसी गलती खोजते हुए जो safe कुल नहीं दिखाएगा।

सुधरा process tokens भेजने से पहले duplicate request पहचानता है। दोनों counters और remembered request IDs वही रहते हैं। पहले कभी accept न हुई ID को remembered list में नहीं रखा जाता। इसलिए उसी ID का छोटा request बाद में आए, तो उसे फिर check किया जा सकता है।

सबूत टेबल हर request, स्वीकृति का कारण और नई स्थिति दिखाती है। पहचान नई हो तो क्षमता के बराबर स्वीकार है; ज़्यादा और दोहरे request कुछ नहीं बदलते। हमेशा का नियम उन अतिरिक्त जाँचों के साथ दिखता है जो असंभव या दोहरे आवंटन रोकती हैं।
